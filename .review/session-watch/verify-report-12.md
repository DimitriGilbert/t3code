## Finding 1 — VERIFIED-DEFECT

- `WatchWidgetSettingsForm.tsx:144-150`: `draftBinding`, `draft`, `initialBinding`, `initialDraft` are all `useState` initializers — they never re-run while mounted. `WatchWidgetBody.tsx:124-131` and `:162-169` render the form with no `key`; `WatchBoard.tsx:286`/`:323` keys shells on `widget.id` only.
- Submit path: `handleSubmit` (form:185-204) builds `config` from stale `draft`/`draftBinding` (though `source` is read fresh at :139, so the stale binding overrides a fresh source — worse than pure-stale). `WatchWidgetBody` passes the _current render's_ `widget` to `onConfigureSubmit` (:128/:167) → `buildWatchWidgetConfigureInput` attaches the fresh `widget.revision` (`watchPages.ts:762-767`).
- Server (`WatchPageService.ts:1089-1112`): `UPDATE ... SET config_json = ? WHERE widget_id = ? AND revision = ?` — wholesale replace guarded only by revision equality, which passes. The clobber is exact.
- Intent check: DESIGN.md:350-351 intends the widget revision to isolate config writes from layout drags, and PRD.md:87-91 makes revision conflicts the anti-clobber mechanism — a stale base that re-bases `expectedRevision` defeats the guard's purpose. Not intentional.
- Fix direction (as reported): remount the form on config change — `key={widget.revision}` at both `WatchWidgetBody` render sites is the smallest fix — or re-derive `draft`/`initialDraft` in an effect on `widget.config` identity change. Coordinate with Finding 2's fix: close-on-success means own-save remount is moot; remote-change remount discards in-progress local edits — consider a "changed elsewhere" hint in that case.

## Finding 2 — VERIFIED-DEFECT

- `handleConfigureSave` (WatchScreen.tsx:619-629): `setConfiguringWidgetId(null)` precedes `configureWidget(...)`; `configuring={props.configuringWidgetId === widget.id}` (:262) gates the form render in `WatchWidgetBody` (:160), so the form unmounts immediately and its `useState` draft is destroyed.
- On `WatchPageRevisionConflictError`: `revisionCheckedCommand` sets `needsReload` (watch.ts:81-87 → banner) and `reportWatchWriteConflict` toasts "Reload ... then retry" (:398-407) — nothing remains to retry. Same for transient failures, which get only a console.warn (Finding 3).
- Fix direction (as reported): move `setConfiguringWidgetId(null)` into the `.then` behind `AsyncResult.isSuccess` (and probably also on any failure once the draft is re-based — but at minimum keep it open on conflict so a retry exists). Pairs naturally with Finding 1's remount/re-base so a conflicted form shows fresh values.

## Finding 3 — VERIFIED-DEFECT

- `useAtomCommand` (use-atom-command.ts:19-21) calls `runAtomCommand` with no reporter → `reporter = console` default (runtime.ts:307); `reportFailure: true` produces only `reporter.warn` (`reportAtomCommandResult`, runtime.ts:420-437).
- `reportWatchWriteConflict` (WatchScreen.tsx:398-407) early-returns unless the squashed cause is `WatchPageRevisionConflictError`. Confirmed reachable silent failures: `WatchLayoutCollisionError` (server :1156), `WatchPageError` ("Watch widget not found." :1103, generic wraps), guard/permission denials inside `revisionCheckedCommand` (watch.ts:76-77), `EnvironmentRpcUnavailableError`/transport.
- Call-site audit confirmed: `renamePage` (:529), `deletePage` (:545), `updatePageScope` (:844-851), `reorderPage` (:855) fire with no `.then`; `duplicatePage`/`restorePage`/`createPage`/`instantiateFromGallery` handle only success; widget ops pipe only through `reportWatchWriteConflict`. The `reportConnectorConfigFailure` pattern (:215-226) exists precisely because the codebase knows these commands need manual toasts — watch page/widget commands lack the equivalent.
- Fix direction (as reported): extend the shared `.then` handler (e.g. rename `reportWatchWriteConflict` → `reportWatchWriteResult`) to also toast non-conflict failures via `squashAtomCommandFailure` + `toastManager.add({type:"error"})`, and attach a result handler to the page ops. Conflict keeps the warning toast + banner; other failures get an error toast.

## Finding 4 — VERIFIED-DEFECT (DUPLICATE of review-report-14 Finding 8)

- Mechanism confirmed: `pending.push` when `listeners.size === 0` (watchUiBus.ts:20-22), full-backlog replay to the first registrant (`pending.splice(0)`, :30), no TTL/dedup/cap.
- Default emitters are gated as reported (`pathname === "/watch"`, CommandPalette.tsx:2288; `watch.editPage` default `when: "watchPageOpen && !editableFocus"`, keybindings.ts:212), so the hazard needs an off-gate emitter — a remapped `watch.editPage` binding hits `CommandPalette.tsx:490-495`, which emits `toggle-edit` unconditionally once the command fires. `open-gallery` (palette :2283) is emitted right after `navigate` and can outlive a redirect: `/watch` `beforeLoad` redirects unauthenticated sessions to `/pair` (routes/watch.tsx:6-12, verified).
- Duplicate note: r14-f8 covers the same root cause and adds two facts this report didn't — the `/pair` redirect path, and that `onWatchUiAction` registers unconditionally at WatchScreen.tsx:771 (before the `watchSupported` early return at :782), so the backlog also flushes onto the unsupported-env screen. One defect, one fix.
- Fix direction (either report's): deliver-once semantics keyed to the post-navigation mount (flush-then-drop on first listener, or scope `pending` to a navigation epoch), TTL on queued actions, or keep-last-only. Bounding to the documented use ("emit right before navigate to /watch") is the intent-faithful fix.
